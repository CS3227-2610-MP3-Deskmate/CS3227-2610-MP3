# Platform

What every feature relies on: the app runs, reports its health, fails without exposing its internals, and starts only when it is safely configured.

### PLT-1 Run a safe placeholder site
Why: Developers and hosts need a running app whose health they can check, and no visitor may see its internals.
- PLT-1.1 (happy) Given the app is running, whether or not the database answers, when anyone requests `GET /`, then the response is `200` with an HTML page whose title and only heading are `Deskmate` and whose only other text is `Deskmate is under construction.`
- PLT-1.2 (happy) Given the database answers, when anyone requests `GET /health/`, then the response is `200` with content type `application/json` and a body that is exactly the JSON object `{"status": "ok"}`.
- PLT-1.3 (failure) Given the app is running and the database refuses connections or rejects the app's credentials, when anyone requests `GET /health/`, then the response is `503` with content type `application/json` and a body that is exactly the JSON object `{"status": "error"}`.
- PLT-1.4 (failure) Given debug is off, when a request's path matches no [route](../TECHNICAL-SPEC.md#routes), even with a trailing slash added, such as `/admin` or `/%3Cscript%3Ealert(1)%3C/script%3E/`, then the response is `404`, and when a request causes an unexpected server error, then the response is `500` and the error and its traceback are written to standard error. Neither response shows internal details: a traceback, an exception message, a file path, a setting's name or value, or the list of routes.
- PLT-1.6 (ambiguous) Given `DJANGO_DEBUG` is unset or is anything other than exactly `true`, including `True`, `1`, `yes`, `true` with spaces around it and the empty string, when the app starts, then debug is off, so errors get the responses in PLT-1.4. Only `DJANGO_DEBUG=true` turns debug on.
- PLT-1.7 (failure) Given a variable that [Configuration](../TECHNICAL-SPEC.md#configuration) requires in the current debug mode is unset or has a value that table does not allow, when the web server or any management command starts, then it exits with a non-zero status without serving a request or running the command, and standard error contains `Deskmate cannot start: <NAME> is not set or is invalid.` for each such variable, but never any variable's value.

Out of scope: The Django admin site and any page other than `/` and `/health/`; custom error pages; styling; HTTPS settings and security headers; the image's production web server, publishing the image and deploying it.

### PLT-2 Release the placeholder site through staging to production
Why: The team needs to check the image visitors will receive and control when a checked staging release reaches production.
- PLT-2.1 (happy) Given a pull request or a candidate release from `main`, when validation runs, then the unchanged [verify command](../../../AGENTS.md#commands) passes and the built image starts with its default production web server, debug off and a throwaway database; a request to its `GET /health/` satisfies PLT-1.2 within the [image readiness deadline](../TECHNICAL-SPEC.md#release-verification). A failed build, startup, check or deadline makes validation fail and prevents that candidate from being published or deployed.
- PLT-2.2 (happy) Given a validated candidate from the current `main`, when its release runs, then the exact validated image is published once with an immutable digest and deployed to staging. Staging succeeds only when the provider confirms that this specific deployment of this digest is live and a subsequent request to staging's HTTPS `GET /health/` satisfies PLT-1.2; a healthy response from an older deployment is insufficient.
- PLT-2.3 (boundary) Given a successful staging release, when production approval is pending or rejected, then production is unchanged. Only approval through the protected GitHub `production` environment permits deployment of the same digest; production succeeds only after the same deployment identity and health checks as staging. Neither environment rebuilds the image.
- PLT-2.4 (failure) Given an attempted deployment, when the provider reports failure, cannot confirm the requested deployment and digest before the [deployment deadline](../TECHNICAL-SPEC.md#release-verification), or the health response does not satisfy PLT-1.2, then the release is unsuccessful, identifies the failing environment and check, and cannot advance. A provider readiness failure before traffic switches retains the previous healthy release, if one exists; on a first deployment there is no previous release to retain. A failed smoke check after traffic switches blocks promotion but does not promise restoration of the previous release. An unconfirmed provider outcome blocks subsequent deployments until the operator establishes its outcome.
- PLT-2.5 (adversarial) Given a pull request, an untrusted workflow run or any source other than `main`, when it runs, then it cannot publish an image, deploy either environment, receive deployment credentials or bypass production approval; [release access controls](../SECURITY-SPEC.md#release-access-and-provenance) enforce these restrictions.
- PLT-2.6 (ambiguous) Given overlapping releases, including one waiting for production approval, when they attempt to progress, then only one release may own staging, the approval wait and production deployment at a time. Immediately before either deployment the release's source commit must still be the current `main`; otherwise it is marked superseded without starting that deployment. An older approval cannot deploy over a newer release.
- PLT-2.7 (happy) Given a successfully deployed environment, when a visitor requests its public HTTPS `/` or `/health/`, then the applicable PLT-1 behaviour is unchanged and the TLS certificate is valid; requests over HTTP redirect to HTTPS. Staging and production have distinct host names.
- PLT-2.8 (adversarial) Given the [hosted environments](../TECHNICAL-SPEC.md#environments), when each app connects to its database, then staging and production use separate databases and credentials, one environment's database credentials cannot authenticate to the other's database, and neither database accepts connections from the public internet. Each app has its own secret key, debug off and an explicit allowed-host list for its own service.

Out of scope: New application pages or features; custom domains; application security headers; automatic rollback after a live deployment; database migration or rollback frameworks; backup automation; availability guarantees during provider or database outages.

Retired: PLT-1.5, PLT-1.8
