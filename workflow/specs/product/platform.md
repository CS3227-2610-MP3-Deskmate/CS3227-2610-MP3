# Platform

What every feature relies on: the app runs, reports its health, fails without exposing its internals, and starts only when it is safely configured.

### PLT-1 Run a safe placeholder site
Why: Developers and hosts need a running app whose health they can check, and no visitor may see its internals.
- PLT-1.1 (happy) Given the app is running, whether or not the database answers, when anyone requests `GET /`, then the response is `200` with an HTML page whose title and only heading are `Deskmate` and whose only other text is `Deskmate is under construction.`
- PLT-1.2 (happy) Given the database answers, when anyone requests `GET /health/`, then the response is `200` with content type `application/json` and a body that is exactly the JSON object `{"status": "ok"}`.
- PLT-1.3 (failure) Given the app is running and the database refuses connections or rejects the app's credentials, when anyone requests `GET /health/`, then the response is `503` with content type `application/json` and a body that is exactly the JSON object `{"status": "error"}`.
- PLT-1.4 (failure) Given debug is off, when a request's path matches no [route](../TECHNICAL-SPEC.md#routes), even with a trailing slash added, such as `/admin` or `/%3Cscript%3Ealert(1)%3C/script%3E/`, then the response is `404`, and when a request causes an unexpected server error, then the response is `500` and the error and its traceback are written to standard error. Neither response shows internal details: a traceback, an exception message, a file path, a setting's name or value, or the list of routes.
- PLT-1.6 (ambiguous) Given `DJANGO_DEBUG` is unset or is anything other than exactly `true`, including `True`, `1`, `yes`, `true` with spaces around it and the empty string, when the app starts, then debug is off, so errors get the responses in PLT-1.4. Only `DJANGO_DEBUG=true` turns debug on.
- PLT-1.7 (failure) Given a variable that [Configuration](../TECHNICAL-SPEC.md#configuration) requires in the current debug mode is unset or has a value that table does not allow, when the web server or any management command starts, then it exits with a non-zero status without serving a request or running the command, and standard error contains `Deskmate cannot start: <NAME> is not set or is invalid.` for each such variable, but never any variable's value.

Out of scope: The Django admin site and any page other than `/` and `/health/`; custom error pages; styling; HTTPS settings and security headers; the image's production web server, publishing the image and deploying it.

### PLT-2 Release the placeholder site to production
Why: The team needs a simple, approved deployment with checks that show whether the public site works.

Proposal for the [review checkpoint](../TECHNICAL-SPEC.md#review-decisions-and-operator-prerequisites): Vercel Hobby and Neon Free are selected; the simplified deployment and removal of app Docker packaging remain proposed, not implemented.

- PLT-2.1 (happy) Given a pull request or push to `main`, when CI runs, then the unchanged [verify command](../../../AGENTS.md#commands), including tests, runs on the runner with temporary PostgreSQL and no stored secrets. Failed verification prevents deployment. The proposed CI has no app-image build/check job; CI success alone does not approve or start production deployment.
- PLT-2.2 (happy) Given successful CI for the current `main` commit and the approval in PLT-2.3, when deployment runs, then only that commit's deployment inputs from a clean checkout are submitted to the fixed Vercel project. Vercel builds its native Python application and automatically assigns the production domain when ready. There is no separate promotion; [deployment verification](../TECHNICAL-SPEC.md#release-verification) records the commit and returned deployment ID.
- PLT-2.3 (boundary) Given a deployment awaiting human approval in the protected GitHub `production` environment, when approval is pending or rejected, then that run creates no deployment. Once approved, success requires the returned deployment ID to have the configured owner/project, production target and `READY` state, the public hostname to map to that ID, and public `/` and `/health/` to satisfy PLT-1.1 and PLT-1.2 within the [deadlines](../TECHNICAL-SPEC.md#release-verification). A healthy previous deployment cannot pass these checks.
- PLT-2.4 (failure) Given a build, deployment or smoke test, when it fails or exceeds its deadline, then the job reports failure and the failing stage. The new version may already be public when a smoke test fails; recovery is manual rollback where available or a fix and new deployment, with no first-release fallback or automatic rollback. A timeout or cancellation may leave Vercel working; deployment is never automatically retried, and the operator must check its outcome before approving any subsequent run.
- PLT-2.5 (adversarial) Given a pull request, untrusted run or source other than `main`, when it runs, then it cannot deploy to the designated Vercel project, receive production database or deployment credentials, or bypass human approval. The project's Git integration is unlinked, so even a pull request changing deployment configuration causes no provider build. The workflow publishes no container image; [release access controls](../SECURITY-SPEC.md#release-access-and-provenance) enforce this boundary independently of editable workflow conditions.
- PLT-2.6 (ambiguous) Given overlapping runs or reruns, when deployment is requested, then one GitHub concurrency group allows only one active deployment job without cancelling it for a newer run. After approval and immediately before deployment, a commit that is no longer current `main` is skipped. Every rerun that deploys requires fresh approval and a new deployment of the checked current commit. Concurrency provides no durable exclusion of provider operations after runner loss; the operator procedure in PLT-2.4 applies to queued runs too.
- PLT-2.7 (happy) Given the app at its configured public `vercel.app` hostname, when a visitor requests HTTPS `/` or `/health/`, then the applicable PLT-1 behaviour is unchanged and the TLS certificate is valid; HTTP redirects to HTTPS. Public access requires no bypass credential. The only persistent app environments are development and production.
- PLT-2.8 (adversarial) Given production configuration, when the app connects to its database or accepts a host name, then it uses production-only database credentials and secret key, debug off, and exactly its public hostname. Database connections require authenticated TLS with system-CA and hostname verification; invalid certificates or hostnames fail without plaintext fallback. Development and temporary CI retain separate databases and credentials; [connection configuration](../TECHNICAL-SPEC.md#configuration) limits plaintext to loopback. Build, deployment and checks do not change production data or schema.

Out of scope: New application pages or features; additional persistent app environments or Preview deployments; custom domains; application security headers; background workers; automatic rollback; schema migrations or production data changes; backup automation; availability guarantees during provider outages, cold starts or free-plan exhaustion.

Retired: PLT-1.5, PLT-1.8
