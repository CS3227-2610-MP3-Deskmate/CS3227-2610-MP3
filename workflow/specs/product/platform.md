# Platform

What every feature relies on: the app runs, reports its health, fails without exposing its internals, and starts only when it is safely configured.

### PLT-1 Run a safe placeholder site
Why: Developers and hosts need a running app whose health they can check, and no visitor may see its internals.
- PLT-1.1 (happy) Given the app is running, whether or not the database answers, when anyone requests `GET /`, then the response is `200` with an HTML page whose title and only heading are `Deskmate` and whose only other text is `Deskmate is under construction.`
- PLT-1.2 (happy) Given the database answers, when anyone requests `GET /health/`, then the response is `200` with content type `application/json` and a body that is exactly the JSON object `{"status": "ok"}`.
- PLT-1.3 (failure) Given the app is running and the database refuses connections or rejects the app's credentials, when anyone requests `GET /health/`, then the response is `503` with content type `application/json` and a body that is exactly the JSON object `{"status": "error"}`.
- PLT-1.4 (failure) Given debug is off, when a request's path matches no [route](../TECHNICAL-SPEC.md#routes), even with a trailing slash added, such as `/admin` or `/%3Cscript%3Ealert(1)%3C/script%3E/`, then the response is `404`, and when a request causes an unexpected server error, then the response is `500` and the error and its traceback are written to standard error. Neither response shows internal details: a traceback, an exception message, a file path, a setting's name or value, or the list of routes.
- PLT-1.6 (ambiguous) Given `DJANGO_DEBUG` is unset or is anything other than exactly `true`, including `True`, `1`, `yes`, `true` with spaces around it and the empty string, when the app starts, then debug is off, so errors get the responses in PLT-1.4. Only `DJANGO_DEBUG=true` turns debug on.
- PLT-1.7 (failure) Given a variable that [Configuration](../TECHNICAL-SPEC.md#configuration) requires in the current debug mode is unset or has a value that table does not allow, when the web server or any management command starts, then it exits with a non-zero status without serving a request or running the command, and standard error contains `Deskmate cannot start: <NAME> is not set or is invalid.` for each such variable, but never any variable's value.

Out of scope: The Django admin site and any page other than `/` and `/health/`; custom error pages; styling; HTTPS settings and security headers; the image's production web server, publishing the image and deploying it.

### PLT-2 Release the placeholder site to production
Why: The team needs to check the image visitors will receive and approve when a validated release reaches production.

Proposal: [hosting and deployment-contract decisions](../TECHNICAL-SPEC.md#pending-hosting-and-deployment-decisions) remain open; these criteria do not establish that deployment is implemented.

- PLT-2.1 (happy) Given a pull request or a candidate release from `main`, when validation runs, then validation succeeds only if the unchanged [verify command](../../../AGENTS.md#commands) passes and the built image starts with its default production web server, debug off and a throwaway database, and its `GET /health/` satisfies PLT-1.2 within the [image readiness deadline and retry rules](../TECHNICAL-SPEC.md#release-verification). A failed build or verification command, an exited server or an expired readiness deadline makes validation fail and prevents that candidate from being published to the designated release image repository or deployed.
- PLT-2.2 (happy) Given a validated candidate from the current `main`, when its release runs, then the exact validated image is published once with an immutable digest to the [designated release image repository](../TECHNICAL-SPEC.md#release-verification), ready for production approval. Successful CI validation or publication alone does not deploy production.
- PLT-2.3 (boundary) Given a validated and published candidate, when production approval is pending or rejected, then production is unchanged. Only explicit human approval through the protected GitHub `production` environment permits deployment of the same digest without rebuilding. The proposed success contract requires confirmation that this specific deployment of this digest is live and a subsequent HTTPS `GET /health/` response satisfying PLT-1.2; a healthy response from an older deployment is insufficient. The provider mechanism for this contract remains pending.
- PLT-2.4 (failure) Given an attempted deployment, when a check has a terminal failure or exhausts the [deployment deadline and retry rules](../TECHNICAL-SPEC.md#release-verification), then the release is unsuccessful and identifies the failing check. A completed health response that fails PLT-1.2 after the requested deployment is confirmed live is terminal. Previous-release retention and first-deployment failure behaviour remain part of the pending hosting contract; this proposal does not promise automatic restoration. An unconfirmed provider outcome blocks subsequent deployments, including after job cancellation or runner termination, until the operator confirms the provider outcome.
- PLT-2.5 (adversarial) Given a pull request, an untrusted workflow run or any source other than `main`, when it runs, then it cannot write to the designated release image repository, deploy production, receive publication or deployment credentials, or bypass production approval. A same-repository pull request that changes its workflow to request `packages: write` is still denied write access to that release package; [registry access controls and protected credentials](../SECURITY-SPEC.md#release-access-and-provenance), independent of editable workflow permissions or conditions, enforce these restrictions.
- PLT-2.6 (ambiguous) Given overlapping releases, including one waiting for production approval, when they attempt to progress, then only one release may own the approval wait and production deployment at a time. Immediately before deployment the release's source commit must still be the current `main`; otherwise it is marked superseded without starting that deployment. An older approval cannot deploy over a newer release.
- PLT-2.7 (happy) Given successfully deployed production, when a visitor requests its public HTTPS `/` or `/health/`, then the applicable PLT-1 behaviour is unchanged and the TLS certificate is valid; requests over HTTP redirect to HTTPS. The production host name and HTTPS provision remain pending hosting decisions.
- PLT-2.8 (adversarial) Given the [development and production environments](../TECHNICAL-SPEC.md#environments), when production connects to its database, then its database and credentials are separate from development and temporary CI databases and credentials. Production uses its own secret key, debug off and an explicit allowed-host list. The production database's network access and transport controls remain pending provider selection.

Out of scope: New application pages or features; custom domains; application security headers; automatic rollback after a live deployment; database migration or rollback frameworks; backup automation; availability guarantees during provider or database outages.

Retired: PLT-1.5, PLT-1.8
