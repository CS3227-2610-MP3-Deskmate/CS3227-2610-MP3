# Platform

What every feature relies on: the app runs, reports its health, presents its pages consistently, fails without exposing its internals, and starts only when it is safely configured.

### PLT-1 Run a safe placeholder site
Why: Developers and hosts need a running app whose health they can check, and no visitor may see its internals.
- PLT-1.1 (happy) Given the app is running, whether or not the database answers, when anyone requests `GET /`, then the response is `200` with an HTML page whose title and only heading are `Deskmate`, whose only other text is `Deskmate is under construction.` and `Sign in`, and which has exactly one link, with the text `Sign in` and the target `/sign-in/`.
- PLT-1.2 (happy) Given the database answers, when anyone requests `GET /health/`, then the response is `200` with content type `application/json` and a body that is exactly the JSON object `{"status": "ok"}`.
- PLT-1.3 (failure) Given the app is running and the database refuses connections or rejects the app's credentials, when anyone requests `GET /health/`, then the response is `503` with content type `application/json` and a body that is exactly the JSON object `{"status": "error"}`.
- PLT-1.4 (failure) Given debug is off, when a request's path matches no [route](../TECHNICAL-SPEC.md#routes), even with a trailing slash added, such as `/admin` or `/%3Cscript%3Ealert(1)%3C/script%3E/`, then the response is `404`, and when a request causes an unexpected server error, then the response is `500` and the error and its traceback are written to standard error. Neither response shows internal details: a traceback, an exception message, a file path, a setting's name or value, or the list of routes.
- PLT-1.6 (ambiguous) Given `DJANGO_DEBUG` is unset or is anything other than exactly `true`, including `True`, `1`, `yes`, `true` with spaces around it and the empty string, when the app starts, then debug is off, so errors get the responses in PLT-1.4. Only `DJANGO_DEBUG=true` turns debug on.
- PLT-1.7 (failure) Given a variable that [Configuration](../TECHNICAL-SPEC.md#configuration) requires in the current debug mode is unset or has a value that table does not allow, when the web server or any management command starts, then it exits with a non-zero status without serving a request or running the command, and standard error contains `Deskmate cannot start: <NAME> is not set or is invalid.` for each such variable, but never any variable's value.

Out of scope: The Django admin site and any page other than `/` and `/health/`; a sign-in form on `/`; custom error pages; styling, which [PLT-4](#plt-4-present-every-page-consistently) covers; HTTPS settings and security headers; the image's production web server, publishing the image and deploying it.

### PLT-2 Release the placeholder site to production
Why: The team needs automatic deployment after a reviewed merge, with a production schema that matches the released code and checks that show whether the public site works.

The production design uses Vercel Hobby and Neon Free under the [operator prerequisites](../TECHNICAL-SPEC.md#review-decisions-and-operator-prerequisites); hosted integration remains to be verified.

- PLT-2.1 (happy) Given a pull request or push to `main`, when CI runs, then the unchanged [verify command](../../../AGENTS.md#commands), including tests, runs on the runner with temporary PostgreSQL and no stored secrets. Failed verification prevents deployment. CI has no app-image build/check job; successful CI starts automatic production deployment only for a same-repository push to `main`.
- PLT-2.2 (happy) Given successful CI for the current `main` commit after merging a pull request approved at its final revision, when deployment runs automatically, then only that commit's deployment inputs from a clean checkout are submitted to the fixed Vercel project. Vercel builds its native Python application and automatically assigns the production domain when ready. There is no separate promotion; [deployment verification](../TECHNICAL-SPEC.md#release-verification) records the commit and returned deployment ID.
- PLT-2.3 (boundary) Given an automatic deployment in the protected GitHub `production` environment, when the release is verified, then success requires the returned deployment ID to have the configured owner/project, production target and `READY` state, the public hostname to map to that ID, and public `/` and `/health/` to satisfy PLT-1.1 and PLT-1.2 within the [deadlines](../TECHNICAL-SPEC.md#release-verification). A healthy previous deployment cannot pass these checks. No separate deployment or rerun approval is required.
- PLT-2.4 (failure) Given a build, including its migration stage, a deployment or a smoke test, when it fails or exceeds its deadline, then the job reports failure and the failing stage; a failed migration fails the build and the job reports it as `deployment: failed`. The new version may already be public when a smoke test fails; recovery is manual rollback where available or a fix and new deployment, with no first-release fallback or automatic rollback, and a rollback restores code but never schema. Any unknown provider or migration outcome, including a lost response, timeout, cancellation, runner loss, a build that may still be migrating, or a failed non-atomic migration, requires the operator to pause automatic deployments, cancel queued deployment runs, reconcile Vercel, confirm which migrations are applied, confirm that no database session still holds the migration lock of PLT-2.14, ending any stale one, and confirm that no earlier operation or migration can complete later before resuming. Neither deployment nor migration is ever automatically retried.
- PLT-2.5 (adversarial) Given a pull request, untrusted run or source other than `main`, when it runs, then it cannot deploy to the designated Vercel project, receive production database or deployment credentials, or bypass required PR review. The project's Git integration is unlinked, so even a pull request changing deployment configuration causes no provider build. The workflow publishes no container image; [release access controls](../SECURITY-SPEC.md#release-access-and-provenance) enforce this boundary independently of editable workflow conditions.
- PLT-2.6 (ambiguous) Given overlapping runs or reruns, when deployment is requested, then one GitHub concurrency group allows only one active release job, including the provider build that migrates, without cancelling it for a newer run. Immediately before submitting the deployment, a commit that is no longer current `main` is skipped, so it neither migrates nor deploys. Every rerun that deploys creates a new deployment of the checked current commit, whose build migrates again, without fresh approval; under PLT-2.14 a rerun after success changes no schema and a rerun after a failure resumes at the first unapplied migration. The concurrency group provides no durable exclusion of provider builds after runner loss, and does not cover a production build started outside the job ([relaxed control](../SECURITY-SPEC.md#release-access-and-provenance)). The migration lock in PLT-2.14 stops two builds migrating at once, but it does not order builds: an earlier in-flight build can still finish after a later release and take the production domain until the operator follows PLT-2.4.
- PLT-2.7 (happy) Given the app at its configured public `vercel.app` hostname, when a visitor requests HTTPS `/` or `/health/`, then the applicable PLT-1 behaviour is unchanged and the TLS certificate is valid; HTTP redirects to HTTPS. Public access requires no bypass credential. The only persistent app environments are development and production.
- PLT-2.8 (adversarial) Given production configuration, when the app or a production migration connects to its database, or the app accepts a host name, then it uses production-only database credentials and secret key, debug off, and exactly its public hostname. Database connections require authenticated TLS with system-CA and hostname verification; invalid certificates or hostnames fail without plaintext fallback. Development and temporary CI retain separate databases and credentials; [connection configuration](../TECHNICAL-SPEC.md#configuration) limits plaintext to loopback. Production credentials stay only where [release access controls](../SECURITY-SPEC.md#release-access-and-provenance) keep them. Production schema and deployment-time data changes occur only through the migration entry point in PLT-2.14, run by a Vercel production build; explicitly specified runtime application writes remain permitted under their existing controls. Given `VERCEL` is set, even to the empty string, and `VERCEL_ENV` is unset or anything other than exactly `production`, as in a preview build, when the migration entry point runs, then it writes only `migration: failed`, exits with a non-zero status and never connects to a database.
- PLT-2.9 (happy) Given an automatic release of the checked current-`main` commit, when Vercel builds its production deployment, then the build runs the migration entry point against the production database before the deployment can become `READY`, so every migration in that commit not yet applied is applied before the public hostname maps to the new deployment; until then the previous deployment keeps serving. Release verification under PLT-2.3 therefore passes only after a successful migration; the public smoke test is unchanged and does not read application tables. [manual]
- PLT-2.10 (failure) Given an automatic release, when the build's migration fails, including because production configuration is missing or invalid (PLT-1.7, with its lines on standard output under PLT-2.12), the database is unreachable or the migration lock is already held, then the build fails, no new deployment receives the production domain, the previous deployment stays public and the job reports `deployment: failed`; `migration: failed` appears only in the migration entry point's output in the provider build log. Recovery follows PLT-2.4. [manual]
- PLT-2.12 (adversarial) Given the migration entry point runs, including a failure whose database error quotes a credential, connection setting, SQL or row value, when it writes to standard output or standard error, then it writes only these lines: `migration: applying <app>.<migration>` before each migration it applies, naming the app label and migration name, or `migration: nothing to apply` when none is unapplied; `Deskmate cannot start: <NAME> is not set or is invalid.` as in PLT-1.7 when configuration is invalid; and, as its last line, `migration: passed` when it finished and no migrations remain unapplied, otherwise `migration: failed`. All of these lines, including the PLT-1.7 line, go to standard output. The PLT-2.8 Vercel check comes before anything else: when it refuses, the entry point loads no settings and writes only `migration: failed`. It never writes credentials, connection settings, environment values, SQL, parameter values, row data, the database's error message or a traceback. This rule covers the entry point's output only, not the rest of the provider build log.
- PLT-2.13 (failure) Given a commit whose data model has changes that its committed migrations do not describe, when the verify command runs, then one of its tests fails, so CI fails and the commit neither migrates production nor deploys; a commit whose migrations match its data model passes that test.
- PLT-2.14 (boundary) Given a database and a commit's committed migrations, when the release's single migration entry point runs, then it applies, in dependency order, only migrations not yet applied and exits with status zero once none remain unapplied; a rerun applies nothing and changes no schema. Every committed migration is atomic, so when one fails, the entry point stops, leaves none of that migration's changes, keeps the migrations applied before it, retries nothing and exits with a non-zero status. For its whole run the entry point holds a lock on the database that only one run can hold at a time, without waiting for it: it takes the lock on its first database connection, before reading or creating any migration record, and uses that one connection until it exits. When another run already holds the lock, the entry point writes only `migration: failed`, applies nothing and exits with a non-zero status. When its connection ends during the run, it applies nothing further, does not reconnect, and ends with `migration: failed` and a non-zero status. The committed build configuration invokes this entry point, and production is migrated through nothing else.

Out of scope: New application pages or features; additional persistent app environments or Preview deployments; custom domains; application security headers; background workers; automatic rollback; reversing migrations or rolling back the schema; deployment-time production data changes other than by migrating; migrating outside a Vercel production build; automatic detection of migrations incompatible with the running version, which is a [review control](../SECURITY-SPEC.md#release-access-and-provenance); waiting or queueing for the migration lock, or ordering builds by commit; separate database roles for migrating; backup automation; availability guarantees during provider outages, cold starts or free-plan exhaustion.

### PLT-3 Call SoC LLM from production
Why: The team needs to know that the deployed app, not only a developer's machine, can authenticate to SoC LLM and get a valid answer, without exposing the key or spending allowance by accident.
- PLT-3.1 (happy) Given `SOC_LLM_PROBE_TOKEN` is set to a valid value and `SOC_LLM_API_KEY` is set to a non-empty value, when a client requests `GET /health/llm/` with the header `Authorization: Bearer <SOC_LLM_PROBE_TOKEN>`, then the app sends exactly the one provider request in [the AI contract](../ai/llm-health.md#request) and, if the provider answers as that contract requires, the response is `200` with content type `application/json` and a body that is exactly the JSON object `{"status": "ok"}`.
- PLT-3.2 (failure) Given `SOC_LLM_PROBE_TOKEN` is set to a valid value, when the probe fails as [the AI contract](../ai/llm-health.md#limits-and-failure) describes, including because `SOC_LLM_API_KEY` is unset or empty, then the response is `503` with content type `application/json` and a body that is exactly the JSON object `{"status": "error"}`, and no provider request is sent when the key is unset or empty. The response never shows the provider's status, headers, body, error message or answer, or the key or token.
- PLT-3.3 (adversarial) Given debug is off, when a `GET` request is made to `/health/llm`, with or without any header, or to `/health/llm/` without a passing token, where a passing token means `SOC_LLM_PROBE_TOKEN` is set to a valid value as [Configuration](../TECHNICAL-SPEC.md#configuration) defines and the request carries exactly one `Authorization` header whose value is exactly `Bearer <SOC_LLM_PROBE_TOKEN>` with one space and a case-sensitive scheme, then the response has the same status, body and headers as PLT-1.4's response for a path that matches no route, is not a redirect, no provider request is sent, and no key or token appears in the response.
- PLT-3.4 (adversarial) Given a request to `/health/llm/`, when it passes ACC-1.8, then `HEAD`, `OPTIONS`, `TRACE`, `POST`, `PUT`, `DELETE` or any other method other than `GET` gets `405` with an empty body before the token gate of PLT-3.3 or any key is read; a `GET` that passes the token gate whose query parameters, form fields, cookies or other headers try to choose the provider URL, model, prompt, key or limits gets the same fixed request in [the AI contract](../ai/llm-health.md#request), and no header from the request is copied to the provider. The `200`, `503`, `405` and `404` responses from this route carry the existing `Cache-Control: no-store` and `X-Frame-Options: DENY` headers.
- PLT-3.5 (boundary) Given a probe request that passes the token gate, including one carrying a session cookie, when it succeeds or fails, then it reads or writes no database record, changes no ticket, article, user or session, and does not sign anyone in or out; with the database unavailable, it still returns PLT-3.1 or PLT-3.2's response (checked with the existing `database_outage` fixture). The app starts and serves every other route whether or not `SOC_LLM_PROBE_TOKEN` or `SOC_LLM_API_KEY` is set, and the probe is the only route that reads either variable.
- PLT-3.6 (boundary) Given a probe request whose provider connection is slow or silent, when 10 seconds pass without a complete response that passes the shape check of [the AI contract](../ai/llm-health.md#output), then the request gives up and gets PLT-3.2's response; it never waits for the platform's 60-second limit and never retries.
- PLT-3.7 (happy) Given both `SOC_LLM_API_KEY` and `SOC_LLM_PROBE_TOKEN` are set only in Vercel production, no `SOC_LLM_*` variable targets Preview or Development, and the app is deployed, when the operator requests `GET https://<hostname>/health/llm/` with `Authorization: Bearer <SOC_LLM_PROBE_TOKEN>`, then the real provider call is made and the response is `200` with a body that is exactly the JSON object `{"status": "ok"}`. The operator records only the result, never the token or key. [manual]

Out of scope: AI features on a role's pages, any LLM input written by a user, ticket, article or workspace, output shown to a user, per-user or global LLM quotas, an audit log of LLM calls, red-team evaluation, automatic probing or monitoring, retries or fallback models, streaming, a new dependency, and any route other than `/health/llm/`.

### PLT-4 Present every page consistently
Why: Pages built feature by feature look inconsistent and are harder to read, and the team needs one presentation that needs no new assets or services.

- PLT-4.1 (happy) Given any HTML page the app serves with its common page layout, including `/`, `/sign-in/`, `/demo-workspace/`, `/requester/`, `/support/`, both roles' ticket and article lists, creation and edit forms, ticket and article detail and reading pages, the resolution form, the Requester password-reset form and every message page such as `Forbidden` or `Too many attempts`, when it is served, then the response itself contains the presentation rules that style it, those rules are the same for every such page, and the response refers to no separate stylesheet, script, font, image or other resource that the browser must fetch. The `/health/` response and the `404` and `500` responses of PLT-1.4 are not affected.
- PLT-4.2 (happy) Given any such page, when it is displayed in a wide browser window, then its content is arranged in one column that leaves space on both sides instead of stretching across the window, so lines of text keep a readable length, and headings, paragraphs, lists, links, form labels, fields, buttons, tables and message pages use consistent type sizes, weights and spacing from page to page. [manual]
- PLT-4.3 (boundary) Given a narrow browser window, when any such page is displayed, then ordinary headings, text, lists, forms and tables stay within the window and can be read without scrolling sideways; only a single unbroken string too long for the window may extend beyond it. [manual]
- PLT-4.4 (failure) Given any such page, when its response and the repository's declared dependencies are checked, then the response itself carries the rules that style it and refers to no stylesheet, script, font, image or other address the browser must fetch, and no new dependency, static-file service or asset pipeline is added, so making static files unavailable or blocking every request but the page's own leaves its presentation unchanged.
- PLT-4.5 (adversarial) Given any such page, when the styling is applied, then it adds no user-visible text, link, form control, image or other element, and changes none of the existing user-visible text, headings, links, form labels, field names, button captions, routes or status codes specified elsewhere.
- PLT-4.6 (adversarial) Given a page that shows saved or resubmitted ticket or article text, or a message page, when it is displayed, then no styling rule hides, reorders or replaces the page's text, and every line break that RQ-1.3, RQ-3.7, KB-1.2 or KB-2.2 shows as a line break still appears as one.

Out of scope: Exact colours, typefaces, type sizes, spacing values or layout measurements; class names, selectors, stylesheet files or a CSS framework or design system; separate static files, a build step or an asset pipeline; JavaScript, images, icons, external fonts or other network requests; custom `404` and `500` pages; dark mode, print styles, animation or other themes; changing page content, structure, routes, status codes or any other behaviour; accessibility conformance or a redesign of the page layout.

### PLT-6 Record internal AI-call audit metadata
Why: Future user AI calls need a shared, privacy-limited record of the metadata their trusted callers explicitly report.

- PLT-6.1 (happy) Given a trusted caller supplies an authenticated stored user and permitted feature and outcome through the [internal audit boundary](../TECHNICAL-SPEC.md#internal-ai-call-audit-boundary), when recording succeeds, then exactly one event is committed with the app's current time, that user's keyed hash and the supplied feature and outcome, and success is returned only after commit. Both reported outcomes can be recorded successfully; repeating an invocation records another event.
- PLT-6.2 (adversarial) Given any audit invocation, when its event or the app's output and logs are inspected, then the event contains only the [audit metadata](../TECHNICAL-SPEC.md#data-model), apart from its record identifier, and no readable user identity, workspace, prompt, answer, provider payload, credential or arbitrary supplied text is retained or emitted by recording; [audit privacy controls](../SECURITY-SPEC.md#internal-ai-call-audit-metadata) govern the keyed hash and error details.
- PLT-6.3 (boundary) Given separate app instances or a restarted app using the same database, when valid invocations succeed, including overlapping invocations, then their committed events share one persistent store and each successful invocation contributes its own event.
- PLT-6.4 (boundary) Given the app samples time T for a valid invocation, when recording commits, then every prior audit event at or before T minus exactly 30 days is deleted, across all users, features and outcomes, and every event newer than that cutoff is retained. Events exactly at the cutoff are deleted. Without a successful invocation there is no scheduled cleanup, so expired events may remain while idle.
- PLT-6.5 (failure) Given an invocation inserts its event and prunes expired events, when the database rejects either operation before commit, then neither operation takes effect; when recording succeeds, both commit together. An invocation inside another transaction is refused before either operation, so its caller cannot later roll back a reported success.
- PLT-6.6 (ambiguous) Given an anonymous, unsaved or non-user input, or a feature or outcome outside the boundary's exact permitted values, including an empty value, different case, surrounding whitespace or a non-string value, when recording is invoked, then it raises the boundary's fixed validation error before any database access and neither inserts nor prunes an event.
- PLT-6.7 (failure) Given a refused connection, database error, or a statement or lock wait reaching its [database bound](../TECHNICAL-SPEC.md#internal-ai-call-audit-boundary), when recording cannot confirm commit, then it raises the boundary's generic database failure, reports no success, and makes no automatic retry. No database message, SQL, row detail or chained driver detail appears in the failure as displayed or logged by the app.
- PLT-6.8 (boundary) Given any existing route or the operator LLM probe succeeds or fails, when it runs, then it invokes no audit recording and creates no audit event; the probe remains database-independent under PLT-3.5. Invoking recording itself makes no provider call, changes no user, session, ticket, article or rate-limit record, and adds no route or user interface.

Out of scope: Building the reserved user AI features; observing or automatically recording provider calls; proving that a reported outcome matches a real call; integrating quotas or the operator probe; reporting, export or an admin viewer; a scheduler, background worker, retry, deduplication or crash-recovery system; new dependencies, services, credentials or settings.

Retired: PLT-1.5, PLT-1.8, PLT-2.11
