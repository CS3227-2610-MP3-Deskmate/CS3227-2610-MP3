# Platform

What every feature relies on: the app runs, reports its health, fails without exposing its internals, and starts only when it is safely configured.

### PLT-1 Run a safe placeholder site
Why: Developers and hosts need a running app whose health they can check, and no visitor may see its internals.
- PLT-1.1 (happy) Given the app is running, whether or not the database answers, when anyone requests `GET /`, then the response is `200` with an HTML page whose title and only heading are `Deskmate` and whose only other text is `Deskmate is under construction.`
- PLT-1.2 (happy) Given the database answers, when anyone requests `GET /health/`, then the response is `200` with content type `application/json` and a body that is exactly the JSON object `{"status": "ok"}`.
- PLT-1.3 (failure) Given the app is running and the database refuses connections or rejects the app's credentials, when anyone requests `GET /health/`, then the response is `503` with content type `application/json` and a body that is exactly the JSON object `{"status": "error"}`.
- PLT-1.4 (failure) Given debug is off, when a request's path matches no [route](../TECHNICAL-SPEC.md#routes), even with a trailing slash added, such as `/admin` or `/%3Cscript%3Ealert(1)%3C/script%3E/`, then the response is `404`, and when a request causes an unexpected server error, then the response is `500` and the error and its traceback are written to standard error. Neither response shows internal details: a traceback, an exception message, a file path, a setting's name or value, or the list of routes.
- PLT-1.6 (ambiguous) Given `DJANGO_DEBUG` is unset or is anything other than exactly `true`, including `True`, `1`, `yes`, `true` with spaces around it and the empty string, when the app starts, then debug is off, so errors get the responses in PLT-1.4. Only `DJANGO_DEBUG=true` turns debug on.
- PLT-1.7 (failure) Given a variable that [Configuration](../TECHNICAL-SPEC.md#configuration) requires in the current debug mode is unset or has a value that table does not allow, when the web server or any management command starts, then it exits with a non-zero status without serving a request or running the command, and standard error contains `Deskmate cannot start: <NAME> is not set or is invalid.` for each such variable, but never any variable's value.

Out of scope: The Django admin site and any page other than `/` and `/health/`; custom error pages; styling; HTTPS settings and security headers; the image's production web server, publishing the image and deploying it.

### PLT-2 Release the placeholder site to production
Why: The team needs automatic deployment after a reviewed merge, with a production schema that matches the released code and checks that show whether the public site works.

The production design uses Vercel Hobby and Neon Free under the [operator prerequisites](../TECHNICAL-SPEC.md#review-decisions-and-operator-prerequisites); hosted integration remains to be verified.

- PLT-2.1 (happy) Given a pull request or push to `main`, when CI runs, then the unchanged [verify command](../../../AGENTS.md#commands), including tests, runs on the runner with temporary PostgreSQL and no stored secrets. Failed verification prevents deployment. CI has no app-image build/check job; successful CI starts automatic production deployment only for a same-repository push to `main`.
- PLT-2.2 (happy) Given successful CI for the current `main` commit after merging a pull request approved at its final revision, when deployment runs automatically, then only that commit's deployment inputs from a clean checkout are submitted to the fixed Vercel project. Vercel builds its native Python application and automatically assigns the production domain when ready. There is no separate promotion; [deployment verification](../TECHNICAL-SPEC.md#release-verification) records the commit and returned deployment ID.
- PLT-2.3 (boundary) Given an automatic deployment in the protected GitHub `production` environment, when the release is verified, then success requires the returned deployment ID to have the configured owner/project, production target and `READY` state, the public hostname to map to that ID, and public `/` and `/health/` to satisfy PLT-1.1 and PLT-1.2 within the [deadlines](../TECHNICAL-SPEC.md#release-verification). A healthy previous deployment cannot pass these checks. No separate deployment or rerun approval is required.
- PLT-2.4 (failure) Given a build, deployment or smoke test, when it fails or exceeds its deadline, then the job reports failure and the failing stage. The new version may already be public when a smoke test fails; recovery is manual rollback where available or a fix and new deployment, with no first-release fallback or automatic rollback. Any unknown provider outcome, including a lost response, timeout, cancellation or runner loss, requires the operator to pause automatic deployments, cancel queued deployment runs, reconcile Vercel and confirm that no earlier operation can complete later before resuming. Deployment is never automatically retried.
- PLT-2.5 (adversarial) Given a pull request, untrusted run or source other than `main`, when it runs, then it cannot deploy to the designated Vercel project, receive production database or deployment credentials, or bypass required PR review. The project's Git integration is unlinked, so even a pull request changing deployment configuration causes no provider build. The workflow publishes no container image; [release access controls](../SECURITY-SPEC.md#release-access-and-provenance) enforce this boundary independently of editable workflow conditions.
- PLT-2.6 (ambiguous) Given overlapping runs or reruns, when deployment is requested, then one GitHub concurrency group allows only one active release job, including its migration, without cancelling it for a newer run. Immediately before migrating and deploying, a commit that is no longer current `main` is skipped, so it neither migrates nor deploys. Every rerun that deploys migrates again and creates a new deployment of the checked current commit, without fresh approval; migrating applies only migrations not yet applied, so a rerun after success changes no schema and a rerun after a failure resumes at the first unapplied migration. Concurrency provides no durable exclusion of provider or migration operations after runner loss. The procedure in PLT-2.4 is manual, without an automatic recovery block; an earlier in-flight provider operation or migration can race a later automatic release before operator intervention.
- PLT-2.7 (happy) Given the app at its configured public `vercel.app` hostname, when a visitor requests HTTPS `/` or `/health/`, then the applicable PLT-1 behaviour is unchanged and the TLS certificate is valid; HTTP redirects to HTTPS. Public access requires no bypass credential. The only persistent app environments are development and production.
- PLT-2.8 (adversarial) Given production configuration, when the app or a production migration connects to its database, or the app accepts a host name, then it uses production-only database credentials and secret key, debug off, and exactly its public hostname. Database connections require authenticated TLS with system-CA and hostname verification; invalid certificates or hostnames fail without plaintext fallback. Development and temporary CI retain separate databases and credentials; [connection configuration](../TECHNICAL-SPEC.md#configuration) limits plaintext to loopback. Production credentials stay only where [release access controls](../SECURITY-SPEC.md#release-access-and-provenance) keep them. The release changes production schema or data only by migrating to the checked commit's committed migrations under PLT-2.9.
- PLT-2.9 (happy) Given an automatic release of the checked current-`main` commit, when it runs, then every migration in that commit not yet applied to the production database is applied after the current-`main` check in PLT-2.6 and before the public hostname maps to the new deployment; until then the previous deployment keeps serving. A commit with no unapplied migrations changes no schema. No new deployment receives the production domain unless migrating succeeded, so release verification under PLT-2.3 passes only after a successful migration; the public smoke test is unchanged and does not read application tables.
- PLT-2.10 (failure) Given an automatic release, when its migration fails, including because production configuration is missing or invalid (PLT-1.7), then no new deployment receives the production domain, the previous deployment stays public, the migration step's output ends with `migration: failed` and the job reports failure and its failing stage as in PLT-2.4. Migrations applied before the failure stay applied; nothing is reversed or retried automatically. Recovery is a fix and a new release, or a rerun once the cause is removed. A migration that is interrupted, loses its connection or outlives the job's deadline is an unknown outcome under PLT-2.4: before resuming, the operator also confirms which migrations are applied and that no earlier migration can still complete.
- PLT-2.11 (boundary) Given a pull request containing a migration, when it is reviewed, then it is approved only if its migrations leave the schema usable by the version in production, because that version keeps serving while and after migrating, after a failed release and after a manual rollback, and the schema is never rolled back. A change that removes, renames or retypes a table or column, or adds a required column without a database default, is split across releases: first code that no longer needs the old shape, then a later migration. Nothing checks this automatically; an incompatible migration that is merged is still applied, the running version can fail until a fix is live, and rollback restores code but not schema. [manual]
- PLT-2.12 (adversarial) Given migrating, including a failure whose database error quotes credentials, connection settings, SQL or row values, when the release logs it, in the job or in a provider build, then the log contains only fixed progress text naming apps and migrations, followed by `migration: passed` or `migration: failed`, and never credentials, connection settings, environment values, SQL, parameter values, row data, the database's error message or a traceback.
- PLT-2.13 (failure) Given a commit whose data model has changes that its committed migrations do not describe, when CI runs, then verification fails, so the commit neither migrates production nor deploys; a commit whose migrations match its data model passes this check.

Out of scope: New application pages or features; additional persistent app environments or Preview deployments; custom domains; application security headers; background workers; automatic rollback; reversing migrations or rolling back the schema; production data changes other than by migrating; automatic detection of migrations incompatible with the running version; migration locking beyond the release concurrency group; separate database roles for migrating; backup automation; availability guarantees during provider outages, cold starts or free-plan exhaustion.

Retired: PLT-1.5, PLT-1.8
