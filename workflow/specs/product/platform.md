# Platform

What every feature relies on: the app runs, reports its health, fails without exposing its internals, and starts only when it is safely configured.

### PLT-1 Run a safe placeholder site
Why: Developers and hosts need a running app whose health they can check, and no visitor may see its internals.
- PLT-1.1 (happy) Given the app is running, whether or not the database answers, when anyone requests `GET /`, then the response is `200` with an HTML page whose title and only heading are `Deskmate` and whose only other text is `Deskmate is under construction.`
- PLT-1.2 (happy) Given the database answers, when anyone requests `GET /health/`, then the response is `200` with content type `application/json` and a body that is exactly the JSON object `{"status": "ok"}`.
- PLT-1.3 (failure) Given the app is running and the database refuses connections or rejects the app's credentials, when anyone requests `GET /health/`, then the response is `503` with content type `application/json` and a body that is exactly the JSON object `{"status": "error"}`.
- PLT-1.4 (failure) Given debug is off, when a request's path matches no [route](../TECHNICAL-SPEC.md#routes), even with a trailing slash added, such as `/admin` or `/%3Cscript%3Ealert(1)%3C/script%3E/`, then the response is `404`, and when a request causes an unexpected server error, then the response is `500` and the error and its traceback are written to standard error. Neither response shows internal details: a traceback, an exception message, a file path, a setting's name or value, or the list of routes.
- PLT-1.6 (ambiguous) Given `DJANGO_DEBUG` is unset or is anything other than exactly `true`, including `True`, `1`, `yes`, `true` with spaces around it and the empty string, when the app starts, then debug is off, so errors get the responses in PLT-1.4. Only `DJANGO_DEBUG=true` turns debug on.
- PLT-1.7 (failure) Given a variable that [Configuration](../TECHNICAL-SPEC.md#configuration) requires in the current debug mode is unset or has a value that table does not allow, when the web server or any management command starts, then it exits with a non-zero status without serving a request or running the command, and standard error contains `Deskmate cannot start: <NAME> is not set or is invalid.` for each such variable, but never any variable's value.

Out of scope: The Django admin site and any page other than `/` and `/health/`; custom error pages; styling; HTTPS settings and security headers; the image's production web server, publishing the image and deploying it.

### PLT-2 Release the placeholder site to production
Why: The team needs to validate a release and approve when its checked production deployment becomes public.

Proposal for the [review checkpoint](../TECHNICAL-SPEC.md#review-decisions-and-operator-prerequisites): Vercel Hobby and Neon Free are selected; the runtime exception, release contract and setup below remain proposed, not implemented.

- PLT-2.1 (happy) Given a pull request or a release candidate from `main`, when CI validates it, then the unchanged [verify command](../../../AGENTS.md#commands), including tests, runs on the runner, and a separate check builds the Docker image and runs Django's checks in it without running tests inside the image. Validation uses temporary PostgreSQL and no stored credentials. A failed verification, build or image check prevents release. CI success alone neither creates a hosted candidate nor approves deployment; the [hosted runtime check](../TECHNICAL-SPEC.md#release-verification) is separate.
- PLT-2.2 (happy) Given a validated current-`main` commit and the human approval in PLT-2.3, when a candidate is created, then Vercel builds its production-target Python artifact from that exact trusted source without assigning the public production hostname. The candidate passes only when its deployment ID, project, source provenance and `READY` state match the release and its protected HTTPS `GET /health/` satisfies PLT-1.2 within the [release deadlines](../TECHNICAL-SPEC.md#release-verification). The candidate uses the production database; a healthy older deployment is insufficient evidence. The Vercel artifact is not the CI Docker image.
- PLT-2.3 (boundary) Given a validated release, when human approval is pending or rejected, then no hosted candidate is created and production is unchanged. Explicit human approval through the protected GitHub `production` environment is required before candidate creation. After candidate validation, only that same deployment ID may be promoted, without rebuilding. Release succeeds only when the public hostname is confirmed to map to that ID and public `/` and `/health/` satisfy PLT-1.1 and PLT-1.2.
- PLT-2.4 (failure) Given candidate creation, validation or promotion, when a terminal failure or [deadline](../TECHNICAL-SPEC.md#release-verification) occurs, then the release is unsuccessful and identifies the failing stage. Before the hostname switches, the previous production mapping is unchanged; on a first release there is no successful live app to preserve. After the switch, a failed check reports failure and requires operator recovery; there is no automatic rollback or promise that the previous version still serves. An unknown create or promote outcome blocks subsequent deployments, including after cancellation or runner termination, until the operator reconciles it.
- PLT-2.5 (adversarial) Given a pull request, an untrusted run or source other than `main`, when it runs, then it cannot create or promote a deployment in the designated Vercel project, receive production database or deployment credentials or the candidate-protection bypass secret, or bypass human approval. Provider Git automation does not build or deploy pull requests, and the workflow publishes no container image; [release access controls](../SECURITY-SPEC.md#release-access-and-provenance) enforce the boundary independently of editable workflow conditions.
- PLT-2.6 (ambiguous) Given overlapping releases, including one waiting for approval, when they progress, then one release owns approval, candidate creation, promotion and final checks at a time. Immediately before candidate creation and again before promotion, its source commit must still be current `main`; otherwise it is superseded without starting that action. An older approval or rerun cannot overwrite a newer release.
- PLT-2.7 (happy) Given the released app is serving on its configured public `vercel.app` hostname, when a visitor requests HTTPS `/` or `/health/`, then the applicable PLT-1 behaviour is unchanged and the TLS certificate is valid; HTTP redirects to HTTPS. The public site requires no deployment-protection bypass credential. The candidate deployment is a version of production, not another persistent app environment.
- PLT-2.8 (adversarial) Given production configuration, when the app connects to its database or accepts a host name, then it uses production-only database credentials and secret key, debug off, and exactly the public hostname plus its current provider-issued deployment hostname. Database connections require authenticated TLS with system-CA and hostname verification; invalid certificates or hostnames fail without plaintext fallback. Insecure production connection settings prevent candidate acceptance. Development and temporary CI retain separate databases and credentials; [connection configuration](../TECHNICAL-SPEC.md#configuration) limits plaintext to loopback. Build, deployment and health checks do not change production data or schema.

Out of scope: New application pages or features; additional persistent app environments or Preview deployments; custom domains; application security headers; background workers; automatic rollback; schema migrations or production data changes; backup automation; availability guarantees during provider outages, cold starts or free-plan exhaustion.

Retired: PLT-1.5, PLT-1.8
