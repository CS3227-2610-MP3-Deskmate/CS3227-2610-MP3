# Accounts

How visitors get accounts and who may open which pages: anyone can create a demo workspace from the sign-in page, users sign in with a username and password, land on their own role's page, and the server refuses the other role's pages. Support Officers can [create additional Requester accounts](#acc-5-create-a-requester-in-the-current-workspace) in their workspace. Signing in, creating accounts or workspaces and Support Officers' [Requester password resets](#acc-4-reset-a-requesters-password) are rate-limited. How users, roles, workspaces and counted attempts are stored is in the [data model](../TECHNICAL-SPEC.md#data-model).

### ACC-1 Sign in and out by role
Why: Each user needs to identify their workspace and reach their own role's pages, and no one may open a role's pages without being signed in with that role.
- ACC-1.1 (happy) Given a signed-out visitor, when they request `GET /sign-in/`, then the response is `200` with an HTML page whose title and top-level heading are `Sign in` and which has a `Username` field, a `Password` field and a `Sign in` button; and when they submit the username and password of an account, then they are signed in and redirected with `302` to their role's page: `/requester/` for a Requester and `/support/` for a Support Officer.
- ACC-1.2 (happy) Given a signed-in user, when they request their role's page, then the response is `200` with an HTML page whose title and top-level heading are `Requester` on `/requester/` and `Support Officer` on `/support/`, and which shows `Signed in as <username>.`, with the username shown as text and never as markup, and a `Sign out` button.

  Every authorized `200` HTML response from either role's landing page or its ticket, knowledge-base, Requester-password-reset or Requester-account-creation pages, including form-validation and AI-result responses, also shows exactly one common plain-text line directly below the top-level heading, before the page-specific content: `Workspace: <code>`. The code is shown only when the user's current stored workspace contains exactly one Support Officer named `support1-<code>` and N Requesters, for an integer N from 2 through 20, named `requester1-<code>` through `requesterN-<code>` with every number present, written in decimal without leading zeros, and no other accounts. All share the same 6-character code with the alphabet of ACC-2.3. This is canonical membership; adding the next numbered Requester under ACC-5 preserves the code. Otherwise, including any extra or missing account, numbering gap, different username, role mismatch, mixed codes or invalid code, the common line is exactly `Workspace: unavailable`; it never substitutes an internal workspace identifier.

  On each request, the label uses the signed-in user's current stored workspace and only that workspace's stored accounts, so changes to the stored workspace, membership, usernames or roles apply from the next request. It is never inferred from the signed-in username alone. Query parameters, form fields, headers and cookies other than the session cookie cannot choose the workspace or displayed code. Resolving the label creates or changes no workspace, account or code. If its database read fails, then, with debug off, the response is the existing generic `500` of PLT-1.4 rather than `Workspace: unavailable`. Rendering any other response, including public pages, redirects and generic error pages, performs no lookup for this common label and adds no workspace line; ACC-2's existing demo-creation response and its `Workspace: <code>` line are unchanged.

  When they press `Sign out`, they are signed out and redirected with `302` to `/sign-in/`, and their old session cookie, even if sent again, gets the signed-out behaviour in ACC-1.4. Signing out happens only on `POST /sign-out/`, which redirects to `/sign-in/` whether or not the visitor was signed in; `GET /sign-out/` gets `405` with an empty body and leaves the user signed in.
- ACC-1.3 (failure) Given a sign-in submission whose username is empty or too long after trimming, contains a character outside the allowlist of ACC-1.7 or is unknown, or whose password is empty or wrong for that username, when it is submitted, then no one is signed in and the response is `200` with the sign-in page, whose only error is `Incorrect username or password.`, whose `Username` field keeps exactly what was typed, shown as text and never as markup, and whose `Password` field is empty. The response for an existing username with a wrong password is the same, apart from its CSRF token, as for an unknown username with the same submission.
- ACC-1.4 (failure) Given a visitor who is not signed in, including one whose session has ended or whose account no longer exists, when they request `GET /requester/` or `GET /support/`, then the response is a `302` redirect to exactly `/sign-in/`, with no query string. Any method other than `GET` on `/requester/` or `/support/` gets `405` with an empty body, whether the visitor is signed out or signed in with either role, unless ACC-1.8 gives `403` first. Given the database does not answer, when a visitor submits the username and password of an account or a signed-in user requests their role's page, then the response is `500` as in PLT-1.4 and the submission signs no one in (see also ACC-3.7).
- ACC-1.5 (adversarial) Given a signed-in Requester requesting `GET /support/`, or a signed-in Support Officer requesting `GET /requester/`, when the request arrives, then the response is `403` with an HTML page whose title and only heading are `Forbidden` and whose only other text is `This page is not for your role.`, and which shows none of the internal details listed in PLT-1.4. The server reads the user's role from their stored account on every request, so a change to the stored role applies from the next request. Nothing else the client sends, such as query parameters, form fields, headers or cookies other than the session cookie, changes which role's pages it may open, and a `next` parameter of any value on the sign-in page or in its submission, such as `https://evil.example/`, `//evil.example/` or the other role's page, does not change where sign-in redirects.
- ACC-1.6 (boundary) Given a user who signed in, when they request their role's page less than 8 hours after signing in, then it is served as in ACC-1.2, and at 8 hours or more after signing in, however active they have been, they are signed out: their role's page behaves as in ACC-1.4, and `/sign-in/` as for a signed-out visitor in ACC-1.1. The session cookie set at sign-in has no `Expires` or `Max-Age` attribute, so the browser drops it when it closes, and a session cookie the browser held before signing in no longer identifies any session once sign-in succeeds. With debug off, the session and CSRF cookies are set with `Secure` and `SameSite=Lax`, and the session cookie also with `HttpOnly`.
- ACC-1.7 (ambiguous) Given a signed-in user, when they request `/sign-in/` by `GET`, or by `POST` with a valid CSRF token, then they are redirected with `302` to their own role's page and stay signed in as the same account, even if the submission holds another account's username and password. For a signed-out visitor whose sign-in attempt is allowed by ACC-3, all whitespace around a submitted username is ignored, where whitespace means exactly these code points: `U+0009`–`U+000D`, `U+001C`–`U+0020`, `U+0085`, `U+00A0`, `U+1680`, `U+2000`–`U+200A`, `U+2028`, `U+2029`, `U+202F`, `U+205F`, `U+3000`; after trimming it must be 1 to 150 characters, each one of ASCII `A`–`Z`, `a`–`z`, `0`–`9`, `@`, `.`, `+`, `-`, `_`. Every other character is rejected as in ACC-1.3, including whitespace within the username and non-ASCII letters, digits, fullwidth forms and other compatibility forms, even if NFKC normalisation would convert them to allowed ASCII. Accepted usernames are compared exactly and case-sensitively, without Unicode normalisation, so `Alice` does not sign in as `alice` and fullwidth `ａｌｉｃｅ` is rejected. Passwords may contain Unicode and match exactly, including case and spaces, with no trimming or normalisation.
- ACC-1.8 (adversarial) Given a request by any method other than `GET`, `HEAD`, `OPTIONS` or `TRACE` to any route without a valid CSRF token, whether or not the visitor is signed in, when it arrives, then, before any other rule applies, the response is `403` with an HTML page whose title and only heading are `Forbidden` and whose only other text is `This form has expired. Go back, reload the page and try again.`, and which shows none of the internal details listed in PLT-1.4; no one is signed in or out. With debug off, such a request with a valid CSRF token gets the same `403`, also before any other rule, if its `Origin` is anything other than exactly `https://<host>` or `http://<host>` for a `<host>` listed in `DJANGO_ALLOWED_HOSTS`, whatever forwarded-scheme header, such as `X-Forwarded-Proto`, it carries: a sign-in or sign-out `POST` with a valid token and `Origin` exactly `https://<host>` is accepted, and one with `Origin: https://evil.example` gets `403`; whether one with `Origin: http://<host>` is accepted is not specified. Responses from `/sign-in/`, `/requester/` and `/support/` carry `X-Frame-Options: DENY`, and those from `/requester/` and `/support/` also carry `Cache-Control: no-store`.

Out of scope: Creating accounts or workspaces, which ACC-2 and [ACC-5](#acc-5-create-a-requester-in-the-current-workspace) cover; rate limiting sign-in attempts, which ACC-3 covers; Requester password resets, which [ACC-4](#acc-4-reset-a-requesters-password) covers; changing or choosing passwords; locking out a username; making failed sign-ins take equal time; which roles may open pages other than `/requester/` and `/support/`; tickets, articles and anything else a workspace holds; creating the database schema in production; a message after signing out; "remember me", signing in by email or single sign-on; security headers other than those in ACC-1.8; the Django admin site; styling, which [PLT-4](platform.md#plt-4-present-every-page-consistently) covers.

### ACC-2 Create a demo workspace
Why: There is no signup or invitation, so a visitor needs a way to get accounts of both roles, in a workspace of their own, without signing in.
- ACC-2.1 (happy) Given a signed-out visitor, when they get the sign-in page, by `GET /sign-in/` or as the response to a failed sign-in in ACC-1.3, then it also has, after the sign-in form, the text `No account? Create a demo workspace with 2 Requesters and 1 Support Officer.` and a second form whose only button is `Create demo workspace` and which sends `POST /demo-workspace/` with no field but its CSRF token. When they press it, then one new workspace is created with exactly three accounts, two Requesters and one Support Officer, and the response is `200` with an HTML page whose title and only heading are `Demo workspace created` and whose only other text is, in order: `Workspace: <code>`, where `<code>` is the 6-character code of ACC-2.3 that the three usernames in the table share; `Copy these passwords now. They will not be shown again.`; a table with the column headings `Username`, `Role` and `Password` and one row for each account, in the order of the usernames in ACC-2.3, giving its username, its role as `Requester` or `Support Officer`, and its password; and a link `Sign in` to `/sign-in/`.
- ACC-2.2 (happy) Given a workspace was just created, when each username and password its page shows is submitted on the sign-in page as in ACC-1.1, then it signs in, both Requesters to `/requester/` and the Support Officer to `/support/`. The three accounts belong to the new workspace and no other account does, and no other workspace or account changes. Creating the workspace signs no one in: afterwards, the visitor who pressed the button still gets the signed-out behaviour of ACC-1.4.
- ACC-2.3 (boundary) Given a workspace is created, then its Requesters' usernames are `requester1-<code>` and `requester2-<code>` and its Support Officer's is `support1-<code>`, where `<code>` is the same 6 characters in all three; each account's password is 16 characters and differs from the other two; and every character of a code or password is one of the 31 characters `23456789abcdefghjkmnpqrstuvwxyz`, drawn as ACC-2.8 says. A code clashes if any of its three usernames is taken when the accounts are saved, including by a creation that finished meanwhile; nothing written under a clashing code remains. When a code clashes, a new code is drawn for all three usernames, up to 3 codes in all, and if all 3 clash, creation fails as in ACC-2.4.
- ACC-2.4 (failure) Given debug is off and the database does not answer, the database fails after part of a workspace has been written, or all 3 codes clash as in ACC-2.3, when a visitor presses `Create demo workspace`, then the response is `500` as in PLT-1.4 and shows no username or password. In either debug mode, no workspace or account from the failed attempt remains.
- ACC-2.5 (adversarial) Given a request to `/demo-workspace/` without a valid CSRF token, or, with debug off, with an `Origin` that ACC-1.8 rejects, such as `https://evil.example`, when it arrives, then it gets the `403` of ACC-1.8; a request by any method other than `POST`, including `GET` and `HEAD`, that ACC-1.8 does not refuse gets `405` with an empty body; and neither creates anything. A valid `POST` that also carries form fields or query parameters, such as `username`, `password`, `role`, `workspace` or `count` with any value, creates the same as one without them: a new workspace with the three accounts of ACC-2.1, named and given passwords as in ACC-2.3, and no account in an existing workspace.
- ACC-2.6 (adversarial) Given a workspace was created, then its passwords appear only in the response to the `POST` that created it: they are stored only as Django's salted hashes and in no session, cookie or other record, and no route shows them again. Sending the same submission again, as a browser does when its user reloads the page and agrees to resend the form, creates another new workspace with different usernames and passwords and shows only those. Every response from `/demo-workspace/` carries `Cache-Control: no-store` and `X-Frame-Options: DENY`. In either debug mode, nothing the app writes to standard output, standard error or its logs, whether creation succeeds or fails as in ACC-2.4, contains a generated username, a generated password or a password hash: when creation fails, the error written as in PLT-1.4 keeps the exception type and traceback but leaves out any database message or detail containing a generated username, password or hash. Tests cover at least a duplicate username on all 3 codes of ACC-2.3, such as `Key (username)=(…) already exists.`, and a database error partway through creation whose detail holds the row being written, such as `Failing row contains (…)` with its password hash.
- ACC-2.7 (ambiguous) Given a signed-in user, when they send `POST /demo-workspace/` with a valid CSRF token, then they are redirected with `302` to their own role's page and stay signed in as the same account, and no workspace or account is created.
- ACC-2.8 (adversarial) Given a code or password is generated, then every character of it comes from the operating system's cryptographically secure random source, independently of every other character and uniformly from the 31 characters of ACC-2.3, with no biased mapping, such as reducing a random byte modulo 31. The security-reviewer checks this by reading the code. [manual]

Out of scope: Rate limiting creating workspaces or signing in, which ACC-3 covers; CAPTCHAs or other limits on them; signup, invitations, and choosing, changing or emailing passwords; Requester password resets, which [ACC-4](#acc-4-reset-a-requesters-password) covers; making a user change a generated password; deleting or expiring workspaces or accounts; showing the passwords again, or hiding them until the user asks; signing the visitor in on creation; sample articles, tickets or anything else a workspace holds; a link to `/sign-in/` from `/`; creating the database schema in production; styling, which [PLT-4](platform.md#plt-4-present-every-page-consistently) covers.

### ACC-3 Rate-limit signing in and creating demo workspaces
Why: Anyone can try to sign in or create a demo workspace without signing in, and each try makes the server hash passwords with a deliberately slow hasher, so scripted tries must neither use up the free plans' CPU allowance or storage, which would pause the site for everyone, nor guess passwords without limit.

[ACC-5](#acc-5-create-a-requester-in-the-current-workspace) also consumes this same creation allowance for Support Officers' Requester-creation POSTs, with that route's access checks and refusal text.

- ACC-3.1 (happy) Given a signed-out visitor, when they send `POST /sign-in/` or `POST /demo-workspace/` and ACC-1.8 does not refuse it, then it is an attempt, a sign-in attempt or a creation, and it is allowed unless the attempts of its kind counted in the 10 minutes before it already reach one of its limits: for sign-in attempts, 10 from its client's address group (ACC-3.5) or 30 from everyone; for creations, 3 from its client's address group or 5 from everyone. An allowed attempt is counted toward both limits of its kind before any password is checked or hashed, and then gets what ACC-1 or ACC-2 says. Sign-in attempts and creations are counted separately, so neither uses up the other's limits.
- ACC-3.2 (failure) Given an attempt that a limit refuses, then, instead of what ACC-1 or ACC-2 says, the response is `429` with a `Retry-After` header as in ACC-3.3 and an HTML page whose title and only heading are `Too many attempts` and whose only other text is `Too many sign-in attempts. Wait a few minutes, then try again.` for a sign-in attempt, or `Too many demo workspaces have been created. Wait a few minutes, then try again.` for a creation. The page shows nothing the request sent and none of the internal details listed in PLT-1.4. No password is checked or hashed, no one is signed in, nothing is created, and the refused attempt counts toward no limit, so attempts sent while refused do not delay when the next one is allowed.
- ACC-3.3 (boundary) Given an attempt counted at a moment T, then it is among the attempts counted in the 10 minutes before each later attempt whose moment, as ACC-3.8 defines it, is before T plus 10 minutes, and not before one whose moment is at T plus 10 minutes or later. A refusal's `Retry-After` is the number of seconds from the refused attempt's moment, rounded up to a whole number, until no limit that refused it would refuse it if nothing else were counted meanwhile, so it is from 1 to 600, even when the app's clock has gone backwards since an attempt was counted. For example, with the clock stopped, when one address group makes 10 sign-in attempts, then an 11th from it at the same moment gets `429` with `Retry-After: 600`, one from it 599.5 seconds later gets `429` with `Retry-After: 1`, and one from it exactly 600 seconds later is allowed; the same holds for 3 creations from one address group, and for 30 sign-in attempts and 5 creations from different address groups.
- ACC-3.4 (ambiguous) Given any limit has been reached, then requests that are not attempts get what ACC-1 and ACC-2 say, and are neither refused by a limit nor counted: a signed-in user's `POST /sign-in/` or `POST /demo-workspace/` is redirected as ACC-1.7 and ACC-2.7 say; `GET /sign-in/` gets the sign-in page; a request that ACC-1.8 refuses gets its `403`, and a method that a route does not list gets `405`; and users already signed in stay signed in, and open their role's page and sign out as ACC-1.2 says. Every allowed attempt is counted however it ends: a sign-in attempt whether or not it signs anyone in and whatever its fields hold, including an empty, unknown or too-long username and an empty password, and a creation even when it fails as in ACC-2.4 after it was counted, such as when the database fails partway or all 3 codes clash.
- ACC-3.5 (adversarial) Given an attempt, then its client address is the last comma-separated entry of its `X-Forwarded-For` header, or, if it has no such header, the address its connection came from. Several `X-Forwarded-For` lines count as one header whose value is theirs joined with commas in the order they arrived, so `X-Forwarded-For: 198.51.100.1` followed by `X-Forwarded-For: 203.0.113.7` gives `203.0.113.7`. Spaces and tabs around the last entry are ignored, so a last entry of `203.0.113.7` with a tab before it and a space after it gives `203.0.113.7`. A header that is present but empty, such as `X-Forwarded-For:` with nothing after it, gives an empty entry, not the connection's address. A valid IPv4 address is four decimal numbers from 0 to 255 separated by dots, none with a leading zero, so `203.0.113.7` is valid and `203.0.113.07` is not; a valid IPv6 address is in the text form of RFC 4291, without brackets, a port or a zone ID, so `2001:db8::1` is valid and `[2001:db8::1]`, `[2001:db8::1]:443` and `fe80::1%eth0` are not. The address's group is the address itself if it is a valid IPv4 address, its first 64 bits if it is a valid IPv6 address, and the group of the IPv4 address it holds if it is an IPv4-mapped IPv6 address such as `::ffff:203.0.113.7`. Every other client address, such as an empty entry, `unknown` or `203.0.113.7:443`, is in one group that all of them share, and so is an attempt with no `X-Forwarded-For` header whose connection address is not valid, such as an empty one. So the entries a client puts before the last change nothing: attempts with `X-Forwarded-For: 198.51.100.1, 203.0.113.7` and `X-Forwarded-For: 198.51.100.2, 203.0.113.7` both count for `203.0.113.7`, and one with `X-Forwarded-For: 203.0.113.7, 198.51.100.9` does not; and `2001:db8:0:1::1` and `2001:db8:0:1:ffff::2` are in one group, but `2001:db8:0:2::1` is not.
- ACC-3.6 (adversarial) Given attempts of one kind that arrive at the same time, including at different server instances, then they are checked and counted one after another against counts kept only in the database, so no limit allows more attempts than its number in any 10 minutes: given 9 sign-in attempts counted from one address group, when 5 more from it arrive together, as tests may make them do by releasing them from a barrier, then exactly 1 is allowed and 4 get the `429` of ACC-3.2. No record that the limits store holds a client address, an address group, a username, a password or anything else the request sent, in any encoding, such as text, hexadecimal or packed bytes. Once an attempt is counted, no record remains of any attempt of its kind counted 10 minutes or more before it; records of the other kind are left as they are. Changing the secret key changes what is stored for the same address group.
- ACC-3.7 (failure) Given the database does not answer, or fails, while an attempt is checked against the limits or counted, or the attempt waits more than 5 seconds to be checked, when the attempt arrives, then no password is checked or hashed, no one is signed in and nothing is created, and with debug off the response is `500` as in PLT-1.4.
- ACC-3.8 (adversarial) Given attempts of one kind that arrive together, then checking each against its limits and counting it are one database transaction, serialised with every other attempt of that kind, which reads the clock only after it stops waiting for them; an attempt never waits for a check of the other kind. An attempt's moment is the later of the clock's time and the time of the latest attempt of that kind already counted, and the attempt is checked against its limits, given its `Retry-After` and, if allowed, counted at that moment, which is also the moment from which ACC-3.6 deletes older records of that kind, so no attempt is counted at a time earlier than one of its kind counted before it, even when the app's clock goes backwards. The security-reviewer checks the serialisation, that neither kind waits for the other, and that the clock is read only after waiting, by reading the code. [manual]

Out of scope: Requester password-reset limits, which [ACC-4](#acc-4-reset-a-requesters-password) covers; CAPTCHAs; creating the database schema in production; limits or lockouts per username, and tools to unlock anyone; emailing anyone; limits on any request that is not an attempt; stopping floods of requests before they reach the app, such as with the hosting provider's firewall; deleting or expiring workspaces, accounts or sessions; changing the limits other than by changing this requirement; telling a visitor how many attempts remain, or any header about the limits but `Retry-After`; making failed sign-ins take equal time; logging refusals; styling, which [PLT-4](platform.md#plt-4-present-every-page-consistently) covers.

### ACC-4 Reset a Requester's password
Why: A Support Officer needs to restore a Requester's access within their own workspace when the Requester cannot use their password.

- ACC-4.1 (happy) Given a signed-in Support Officer, when they open their role's page, then it also has a `Reset Requester password` link to the reset form. Opening that form returns `200` with the title and top-level heading `Reset Requester password`, one empty single-line field labelled `Username`, a `Reset password` button and a `Support Officer` link back to their role's page. There is no account list or app-provided username suggestion.
- ACC-4.2 (happy) Given a submission selecting a Requester in the signed-in Support Officer's current stored workspace, when the reset succeeds, then only that Requester's password hash is replaced with a new Django salted hash of a freshly generated 16-character password, using the alphabet and independent, uniform, cryptographically secure draws of ACC-2.3 and ACC-2.8. The response is `200`, without a redirect, with the title and only heading `Requester password reset` and whose only other text is, in order: the common workspace line of [ACC-1.2](#acc-1-sign-in-and-out-by-role); `Copy this password now. It will not be shown again.`; a table with column headings `Username` and `Password` and one row containing the selected Requester's stored username and generated password; and a `Support Officer` link back to their role's page. The generated password can be used to sign in as that Requester under ACC-1; no one is signed in by resetting it.
- ACC-4.3 (boundary) Given a reset submission, then its `username` form value follows exactly ACC-1.7's whitespace trimming, 1-to-150-character ASCII allowlist and exact case-sensitive comparison, without Unicode normalisation; a missing value counts as empty, and if that form field occurs more than once, its last value is used. An empty, malformed, too-long or unknown username, a Support Officer's username including the caller's, and a Requester's username outside the caller's current stored workspace all get the same `200` reset form with the sole error `No Requester with that username was found in your workspace.` and no generated password. The field retains the submitted value as escaped text, with each CRLF pair and each remaining CR or LF displayed as one space and null characters as `�`; a missing value is displayed empty. No account or session changes, and the page discloses no stored account details. For the same submitted value, the response is the same apart from its CSRF token whether it is unknown, belongs to a Support Officer or belongs to another workspace.
- ACC-4.4 (ambiguous) Given a successful reset, then all sessions that authenticated as the selected Requester before that reset, including in other browsers, cease to authenticate: their next request requiring sign-in gets ACC-1.4's signed-out behavior, and replaying their cookies does not restore access. Other users' sessions, including the calling Support Officer's, are unaffected. Reopening the reset form shows an empty form and no password; each permitted resubmission is a new reset with a fresh random draw, not a replay of an earlier result. When resets overlap, only the last committed password hash remains, so a password shown by an earlier successful response may already have been superseded. Requests already authenticated before the reset are not cancelled.
- ACC-4.5 (adversarial) Given a request to the reset route, then the existing CSRF and Origin checks, method refusal, signed-out redirect, stored-role denial and session expiry apply in the order in [Routes](../TECHNICAL-SPEC.md#routes), before target lookup or password generation. The caller's role and workspace are read once from their stored account during that request's access check and used for the rest of that request. Only the `username` form value selects the target; at the password update, the target must still exist with the Requester role in that workspace. If the target was deleted, moved to another workspace or given another role between lookup and update, so no qualifying account remains, then the reset changes no account or session and returns exactly ACC-4.3's generic rejection, with no generated password shown. Extra form fields and all query parameters, including `username`, `password`, user identifiers, `workspace`, `role` and `next`, cannot select a different target or workspace, choose a password, change account attributes or redirect the result. No rejected request changes any account's password hash; existing session expiry and invalid-session cleanup still apply.
- ACC-4.6 (adversarial) Given any reset response, then the cache, framing, plaintext-retention and log controls in [Requester password resets](../SECURITY-SPEC.md#requester-password-resets) apply. The generated password appears only in the successful reset POST response, except that existing local Django exception pages with `DEBUG=True` may also show it in local variables under [Error pages, health check and logs](../SECURITY-SPEC.md#error-pages-health-check-and-logs). With `DEBUG=False`, error responses expose no generated password. No route recovers a previously generated password. Submitted and stored usernames are always displayed as text, never markup.
- ACC-4.7 (failure) Given debug is off, when the database does not answer while opening or submitting the reset form, or generating, hashing or saving the password fails before the save can be confirmed, except an ineligible target rejected under ACC-4.5, then the response is the generic `500` of PLT-1.4, with no success page or generated password. In either debug mode, a database-rejected or rolled-back reset leaves the stored password hash and existing sessions' ability to authenticate unchanged. If a connection fails after the database committed, or the successful response is lost, the reset may already have taken effect and invalidated the old sessions; the generated password cannot be recovered, and submitting again is another reset under ACC-4.4. There is no automatic retry or recovery of a lost response.
- ACC-4.8 (adversarial) Given a reset POST that passes the method and access checks of ACC-4.5, then it is a reset attempt, checked and counted before username validation, target lookup, password generation or hashing, using a separate kind of the existing limiter. It is allowed unless reset attempts counted in the preceding 10 minutes already reach 3 from its client's address group or 5 from everyone. It reuses ACC-3.3's window boundary and `Retry-After` calculation, ACC-3.5's address grouping, ACC-3.6's shared database counts, privacy and cleanup, ACC-3.7's fail-closed behavior and 5-second wait limit, and ACC-3.8's per-kind serialisation and clock rules, independently of both sign-in and creation attempts. Every allowed reset attempt is counted even if its username is rejected or the reset subsequently fails; a request failing CSRF, Origin, method or access checks, a GET, and a limit-refused attempt are not counted. A limit-refused attempt returns `429` with `Retry-After` as above, the title and only heading `Too many attempts` and the sole other text `Too many password resets. Wait a few minutes, then try again.`, with no request data or internal details from PLT-1.4, no password generated or hashed and no password or session changed. Database failure or an excessive wait while checking or counting resets no account and generates or hashes no password; with debug off it returns PLT-1.4's generic `500`. Reset attempts neither consume nor wait for sign-in or creation allowances, and those attempts neither consume nor wait for the reset allowance. A reset hashes its generated password once.

Out of scope: Self-service recovery; resetting Support Officer passwords; username discovery or a requester directory; account creation, deletion, activation, role or workspace changes; choosing or changing a password directly; email, invitations, recovery tokens or links; making a Requester change a generated password; reset history, audit trails or notifications; recovery or redisplay of a generated password; reauthentication of the Support Officer; new services, dependencies, credentials or deployment changes; styling, which [PLT-4](platform.md#plt-4-present-every-page-consistently) covers.

### ACC-5 Create a Requester in the current workspace
Why: A Support Officer needs to give additional Requesters access to their existing workspace while preserving its code and bounding its membership.

- ACC-5.1 (happy) Given a signed-in Support Officer, when they open their role's page, then it also has a `Create Requester account` link to the creation form. Opening that form returns `200` with the title and top-level heading `Create Requester account`, the common workspace line of ACC-1.2, the text `Create one Requester account in this workspace.`, a form with only its CSRF token and a `Create account` button, and a `Support Officer` link back to their role's page. When an admitted submission creates an account, then the response is `200`, without a redirect, with the title and only heading `Requester account created` and whose only other text is, in order: the common workspace line; `Copy this password now. It will not be shown again.`; a table with column headings `Username` and `Password` and one row containing the new account's username and generated password; and a `Support Officer` link back to their role's page. These credentials sign in as the new Requester under ACC-1. Creation signs no one in or out and changes no existing account, workspace, ticket, article or session.
- ACC-5.2 (boundary) Given a creation POST admitted under ACC-5.7, when the caller's current stored workspace has canonical membership under ACC-1.2 with N below 20, then it creates exactly one Requester named `requester<N+1>-<code>` in that workspace. Its password is a fresh 16-character draw using ACC-2.3's alphabet and ACC-2.8's independent, uniform, cryptographically secure draws, hashed once with Django's salted hasher. The limit is 20 total stored Requesters in each workspace, including the initial two and excluding Support Officers; there is no aggregate lifetime account cap across workspaces. If the workspace already has 20 or more stored Requesters, then the response is the `200` creation form with the sole error `This workspace already has 20 Requester accounts.` Otherwise, if membership is not canonical, it is the same form with the sole error `Requester accounts cannot be created for this workspace.` These rejections generate or hash no password and create or change no account; their common workspace line still follows ACC-1.2.
- ACC-5.3 (ambiguous) Given permitted repeat or overlapping submissions, then each successful submission creates a separate next-numbered account with a fresh password draw; resending a successful POST is another creation, not a replay. Reopening the form shows no credentials. Checking the stored membership and Requester count and inserting the next account are one atomic operation, serialized per workspace: from 19 Requesters, two overlapping admitted submissions produce exactly one new account and one quota rejection under ACC-5.2. A required next username already held by any account outside that canonical membership, including one saved meanwhile, fails under ACC-5.6; creation never skips a number, draws another code, overwrites an account or changes its workspace or role.
- ACC-5.4 (adversarial) Given a request to the creation route, then CSRF and Origin checks, method refusal, signed-out redirect, stored-role denial and session expiry apply in the order in [Routes](../TECHNICAL-SPEC.md#routes), before membership checks or password generation. Only `GET` and `POST` are accepted. The caller's role and workspace are read once from their stored account during that request's access check and used for the rest of that request. Only a Support Officer can create an account, and only in that stored workspace. Extra form fields and all query parameters, including `username`, `password`, `role`, `workspace`, `code`, `count` and `next`, cannot choose credentials, attributes, quantity, workspace or a redirect, and are not displayed. Rejected requests create or change no account; existing session expiry and invalid-session cleanup still apply.
- ACC-5.5 (adversarial) Given any creation-route response, then the cache, framing, plaintext-retention and log controls in [Requester account creation](../SECURITY-SPEC.md#requester-account-creation) apply. A generated password appears only in the successful creation POST response, except that existing local Django exception pages with `DEBUG=True` may show it in local variables under [Error pages, health check and logs](../SECURITY-SPEC.md#error-pages-health-check-and-logs). With `DEBUG=False`, error responses expose no generated credentials or password hash. No route recovers a previously generated password. Usernames are always displayed as text, never markup. Generic non-`200` responses perform no common-label lookup and show no workspace line, as ACC-1.2 requires.
- ACC-5.6 (failure) Given debug is off, when the database does not answer while opening or submitting the form, the next username clashes under ACC-5.3, or generating, hashing or saving fails, then the response is the generic `500` of PLT-1.4 with no success page or generated credentials. In either debug mode, a database-rejected or rolled-back creation leaves no new account and changes no existing account or session. If failure occurs after commit, including while rendering the response, or a connection or successful response is lost after commit, the account may already exist; its password cannot be recovered, and submitting again is another creation under ACC-5.3. There is no automatic retry or recovery of a lost response.
- ACC-5.7 (adversarial) Given a creation POST that passes ACC-5.4's method and access checks, then it is checked and counted in the same creation allowance as ACC-3.1's demo-workspace POSTs, before membership or quota checks, validation, generation or hashing. The two routes share both the client-address-group and everyone counts, with no new allowance or attempt kind; sign-in and reset allowances remain independent. It reuses ACC-3.3's window and `Retry-After` calculation, ACC-3.5's address grouping, ACC-3.6's shared counts, privacy and cleanup, ACC-3.7's fail-closed behavior and 5-second wait limit, and ACC-3.8's per-kind serialization and clock rules. Checking and counting commits before any password is hashed. Every allowed attempt is counted, including quota or noncanonical-membership rejections, username clashes and downstream failures; a GET, a request failing CSRF, Origin, method or access checks, and a limit-refused attempt are not counted. A limit refusal returns `429` with `Retry-After`, the title and only heading `Too many attempts` and the sole other text `Too many account creation attempts. Wait a few minutes, then try again.`, with no request data or internal details from PLT-1.4, no password generated or hashed and no account created or changed. Database failure or an excessive wait while checking or counting generates or hashes no password and creates or changes no account; with debug off it returns PLT-1.4's generic `500`.

Out of scope: Creating Support Officer accounts; custom usernames or passwords; account lists or username suggestions; invitations, email or signup; deleting, expiring, moving or changing roles of accounts; changing existing passwords, which [ACC-4](#acc-4-reset-a-requesters-password) covers; password redisplay or recovery; repairing noncanonical membership; durable workspace codes or schema changes; quota settings or a global lifetime cap; new rate-limit kinds, services, dependencies, credentials or deployment changes; styling, which [PLT-4](platform.md#plt-4-present-every-page-consistently) covers.
