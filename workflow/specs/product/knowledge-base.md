# Knowledge base

Support Officers write and edit plain-text articles in their own workspace. The [data model and routes](../TECHNICAL-SPEC.md#data-model) and [security controls](../SECURITY-SPEC.md#knowledge-base-authoring) have their own homes.

### KB-1 Write and edit knowledge-base articles
Why: Support Officers need to record reusable guidance and reopen it to keep it accurate.
- KB-1.1 (happy) Given a signed-in Support Officer, when they open their role's page, then it also has a `Knowledge base` link to the article list. The list returns `200`, has the title and top-level heading `Knowledge base`, a `New article` link to the creation form and a `Support Officer` link back to their role's page. It shows every article in their workspace in creation order, earliest first, as its saved title linking to its edit form; if there are none, it shows `No articles yet.` instead of article links.
- KB-1.2 (happy) Given a signed-in Support Officer, when they open the creation form, then it returns `200` with the title and top-level heading `New article`, empty fields labelled `Title` and `Body`, a `Save article` button and a `Knowledge base` link back to the list. `Title` is a single-line text field and `Body` is a multiline text field. When they submit valid values with `Save article`, then exactly one article is saved in their workspace and the response is a `302` redirect to its edit form; the resulting `GET` shows its saved values, and refreshing that `GET` creates nothing.
- KB-1.3 (happy) Given an article in a signed-in Support Officer's workspace, when they open its edit form, then it returns `200` with the title and top-level heading `Edit article`, the fields, button and list link of KB-1.2, and the article's saved values in the fields. When they submit valid values, then both fields of that article are replaced together, no article is created, and the response is a `302` redirect to the same edit form. Reopening it, including in another signed-in session, shows the saved values. Any Support Officer in that workspace may edit the article.
- KB-1.4 (boundary) Given a creation or edit submission, then `CRLF` and `CR` line endings in `Body` become `LF`, and Unicode whitespace around each field is removed before validation and saving; nothing else is normalised. `Title` must contain 1 to 200 Unicode code points and `Body` 1 to 10000 after those changes. Neither may contain a null character, and `Title` may contain no remaining `CR` or `LF`. A missing field counts as empty. When either field is invalid, then nothing is saved and the response is `200` with the same form, retaining the raw submitted values as text except for these display-only changes: in the single-line `Title`, each `CRLF` pair and each remaining `CR` or `LF` is shown as one space; in the multiline `Body`, line endings are displayed as newlines; in either field, null characters are shown as `�`. Only the invalid fields have errors: `Enter a valid title (1 to 200 characters).` for `Title` and `Enter a valid body (1 to 10000 characters).` for `Body`.
- KB-1.5 (ambiguous) Given valid submissions, then equal titles are allowed and separate creation submissions, including a resend of the same submission, create separate articles. When an edit form was opened before another edit saved, submitting it still saves both submitted fields: the last successful save replaces the preceding title and body together, with no stale-edit warning or merge. An invalid or database-rejected submission never replaces a successful save.
- KB-1.6 (adversarial) Given a request to an article route, then the existing signed-out redirect, stored-role denial, session expiry and CSRF behavior of ACC-1.4–ACC-1.6 and ACC-1.8 applies, with the method and access order in [Routes](../TECHNICAL-SPEC.md#routes). A Requester gets the role-denial response before any article is looked up. Article responses use the existing cache and framing controls in [Knowledge-base authoring](../SECURITY-SPEC.md#knowledge-base-authoring). No rejected request creates or edits an article.
- KB-1.7 (adversarial) Given a signed-in Support Officer, when they request an edit form or submit an edit for an article outside their workspace or an identifier that does not exist, then both get the same generic `404` behavior of PLT-1.4, with no article title or body, and nothing changes. The current stored workspace determines the list and every create or edit; extra form fields and query parameters, including an article identifier, workspace or role, cannot change that workspace or the article selected by the route. All article text, including saved text and invalid values shown again, is displayed as text, never as HTML or rendered Markdown.
- KB-1.8 (failure) Given debug is off, when the database does not answer while opening the list or a form, or a database operation fails before a save can be confirmed, then the response is the generic `500` of PLT-1.4, with no success redirect. A database-rejected or rolled-back creation leaves no new article, and a database-rejected or rolled-back edit leaves both saved fields unchanged. In either debug mode, a save writes both fields together. If the connection fails after the database committed, the save may already have taken effect; reopening the list or form shows the stored result once the database answers. No automatic retry or recovery of unsaved form contents is promised.

Out of scope: Requesters reading articles; public browsing; search, filtering, pagination or ordering controls; AI; rich text or Markdown rendering; attachments; publishing states; deletion; author attribution, timestamps, history or audit trails; stale-edit detection, conflict resolution or recovery of unsaved changes; article quotas or rate limits; new dependencies, services, credentials or deployment changes; styling.
